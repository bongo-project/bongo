## Phase 13: DNSBL / blocklist checks

PRD: [prd-dnsbl-blocklist-checks.md](active/prd-dnsbl-blocklist-checks.md).
Adds configurable DNS blocklist lookups on inbound mail — the cheapest reputation signal there is,
and currently absent: inbound scoring never consults the connecting IP at all.

**A listing SCORES, it never rejects.** That is not timidity, it is experience: on 2026-08-17 this
server was listed on `b.barracudacentral.org` having never sent a single message, purely because the
hosting provider recycled the IP. A receiver configured to reject on that listing would have
silently discarded legitimate mail with only a 5xx to show for it. Blocklists are useful evidence
and poor verdicts.

**Verified before import (the PRD predates two of these):**
- FR-7's trust skip is now directly implementable — `env.GetTrusted()` exists as of Phase 12
  (`builtin.go:169`). The PRD was written when it did not.
- The `DNSResolver` seam the PRD wants to reuse exists at `internal/mail/spf.go:41` with
  `LookupTXT` and `LookupIP`, so DNSBL's A-record queries fit it without a new abstraction.
- `proxy_protocol = true` on prod, so the connecting IP really is the client's. This is the
  PRD's decisive caveat and it is already satisfied — but see 13.5, because it stops being true
  if bongo is moved to face the internet directly without clearing that flag.

| B13 | **(research PRD) Backup that scales past a few GB.** Operator raised 2026-08-22: the current backup does not survive hundreds/thousands of accounts. Correct, and it is THREE problems. (1) **Duplication** — `backup-extras.sh` tars everything nightly, but blobs are content-addressed and immutable, so it re-copies all historical mail to capture one day of new mail. (2) **Downtime stops being free** — measured 2026-08-22: 11.6s stop->start, entirely graceful shutdown, because tar of ~26MB is instant. gzip runs ~50MB/s, so past roughly 1GB the window becomes tar-bound and grows linearly; at 100GB it is an hour of nightly downtime. (3) **Restore time** — RTO becomes hours. **The fix the architecture already supports:** split the halves. Blobs are immutable -> incremental/dedup backup (restic/borg), nightly cost proportional to NEW mail. Pebble is small and mutable and supports CHECKPOINTS — a consistent snapshot while running, which bongo already uses in `FSM.Snapshot`. Together that removes the container stop entirely. **Ordering is load-bearing: snapshot Pebble FIRST, then copy blobs.** Delivery writes the blob before recording metadata, so every blob referenced by the snapshot already exists; the reverse order can capture metadata pointing at an uncopied blob. Also worth covering in the PRD: interaction with blob GC (currently `dryrun`), whether per-user restore is wanted at that scale (tar-of-everything cannot do it), and verifying the new scheme with `verify-restore.sh`.
